Övergången från att göra för hand till att automatisera dessa processer innebar att abstraktionsnivån steg; Ändringar i konfigurationsfiler istället för att manuellt ändra filer eller exekvera dem. 

Gällande automation: Av de delmoment jag gjorde är secrets (maskering) något som kan vara riskabelt att automatisera, där risken är att känslig information (t.ex GITHUB_TOKEN som i uppgiften) sparas i något skede (sparas efter körningen, pågrund av ett misstag i instruktionerna/logiken) eller pushas eller på annat sätt blir synlig/exponeras; Till exempel API-nycklar, lösenord, SSH certificates (metadata för SSH-nycklar) eller liknande information som potentiellt kan användas för att få otillåten tillgång till system. Ett bra exempel på situationer var detta sker, dock simulerat: CTF (Capture the flag) uppgifter där någon hemlighet har blivit kvar någonstans eller sparas till en directory som den inte borde vara i. För databaser är det förstås omöjligt att inte automatisera hantering av känslig information (där det finns risker som XSS/cross-site scripting etc), och för processer som man vet att kommer köras upprepade gånger är det mer logiskt att automatisera, men för processer som antingen körs en gång, endast några gånger eller med oregelbundna mellanrum/intervall kan det vara bättre att göra det manuellt, speciellt om man vill en väldigt anpassad konfiguration/custom configs.
